## PART 1 — LICENSE ANALYSIS

### 1. AGPLv3 §13 and §5 in plain English

**§13 — Remote Network Interaction (this is the clause that makes AGPL different from ordinary GPL).** Verbatim from `LICENSE.txt` lines 540–558:

> "Notwithstanding any other provision of this License, if you modify the Program, your modified version must prominently offer all users interacting with it remotely through a computer network (if your version supports such interaction) an opportunity to receive the Corresponding Source of your version by providing access to the Corresponding Source from a network server at no charge..."

Plain English: ordinary GPL only forces you to hand over source code if you *distribute* (convey) copies of the binary. Running a modified GPL program privately on your own server and letting people use it over the web was never "conveying" — that's the famous "ASP/SaaS loophole." AGPL §13 closes it: if you **modify** the AGPL'd program and let people **interact with it remotely over a network** (i.e., it's a web app, an API, anything with a server component), you must offer *those users* the modified source code, free, via the server itself — even though you never shipped them a copy of the binary. Confirmed by the AGPL's own preamble at lines 40–46: "It requires the operator of a network server to provide the source code of the modified version running there to the users of that server." (`LICENSE.txt` lines 40-46). This is also independently corroborated by industry legal writing: "AGPL was written to close [the] 'ASP loophole'... Under Section 13, if users interact with AGPL'd software remotely, you must offer them the corresponding source." — [Mend.io, "The SaaS Loophole In GPL Open Source Licenses"](https://www.mend.io/blog/the-saas-loophole-in-gpl-open-source-licenses/), accessed 2026-07-25, Medium confidence (industry legal-compliance vendor blog, not a law firm, but consistent with the license text itself which is the primary source).

**§5 — Conveying Modified Source Versions.** Verbatim, `LICENSE.txt` lines 196–226. If you convey (distribute/publish/hand out copies of) a modified version, four conditions attach:
- (a) mark that you modified it, with a date;
- (b) carry notice that it's released under AGPL;
- (c) **"You must license the entire work, as a whole, under this License to anyone who comes into possession of a copy."** — this is the copyleft "poison pill": the *whole* modified work, not just the parts you touched, must be relicensed AGPL;
- (d) interactive UIs must show Appropriate Legal Notices (copyright + no-warranty + "how to get the license").

§5 also defines "mere aggregation" (lines 220-226, quoted in full in §4 below) — separate, independent programs bundled together on the same medium do **not** become AGPL just by sitting next to AGPL code.

### 2. THE DECISIVE QUESTION — does Rob's private CRM trigger §13?

Three scenarios, precisely distinguished:

**(a) Internal-only use by Rob's own sales reps, nobody outside the company.** Per §0 Definitions (`LICENSE.txt` lines 84-86): *"To 'convey' a work means any kind of propagation that enables other parties to make or receive copies. **Mere interaction with a user through a computer network, with no transfer of a copy, is not conveying.**"* Rob's own W-2/1099 sales reps, acting as agents of the same legal entity (AI VoiceTech), using an internal tool over the company's own network, are not "other parties" receiving a copy — they're the same operator using their own software. §2 Basic Permissions reinforces this: *"You may make, run and propagate covered works that you do not convey, without conditions..."* — running modified AGPL code purely internally, never conveyed to anyone outside the organization, **does not trigger §5 or §13 at all.** This is the single most important fact in this analysis: **a private internal CRM used only by Rob's own employees, never exposed to anyone outside AI VoiceTech, is not "interacting with users remotely" in the AGPL sense, because there is no external "other party."** This is the consensus reading among AGPL-compliance commentators as well — "SaaS use of an unmodified AGPL program... does not trigger copyleft," and even for modified code, the operative trigger is specifically about *users outside the operating organization* accessing it over a network. ([Mend.io](https://www.mend.io/blog/the-saas-loophole-in-gpl-open-source-licenses/), accessed 2026-07-25, Medium confidence.)

Caveat: this "single organization" reading is well-established for GPL-family licenses generally (contractors/employees "on your behalf, under your direction and control" are explicitly carved out at §2 lines 149-155: *"You may convey covered works to others for the sole purpose of having them make modifications exclusively for you... Those thus making or running the covered works for you must do so exclusively on your behalf, under your direction and control..."*), but it has **not been tested in litigation for AGPL specifically**. If AI VoiceTech ever has semi-independent contractors, resellers, or a separate legal entity (e.g., a spun-out subsidiary, a joint venture with a title company) using the same instance, the "one organization" boundary gets blurry fast — that's exactly the kind of edge case worth the $500 attorney conversation in §8.

**(b) Use by external customers over the network.** This is unambiguously "interacting with it remotely through a computer network" under §13. The moment a client — a roofing contractor, a real-estate/title company — logs into a CRM instance that contains modified Macro code, over the internet, §13's trigger condition is met. If Rob modified the Program (which he would — customizing a CRM is modification, not verbatim use), he is now obligated to **prominently offer those external users the Corresponding Source of his modified version, free, from a network server.** That means: the roofing contractor client using his CRM could legally demand — and he'd be obligated to hand over — the full modified source code of the CRM, including whatever proprietary sales logic, prompts, integrations, or business rules he built on top of Macro. This is likely the single worst outcome for Rob's stated strategy (proprietary tooling, no upstream attribution, building toward acquisitions) and is explored further in §4 and §6.

**(c) A white-labeled instance embedded on a client's site.** Same trigger as (b), arguably worse: the client's own end-customers (e.g., a title company's home-buying clients) are now also "users interacting with it remotely," each entitled to demand source. White-labeling does nothing to escape AGPL — the license attaches to the *code*, not the *branding*. There is no concept of "internal" once it's embedded on a third party's site for that third party's outward-facing customers.

**Bottom line on Q2:** Internal-only, single-entity use = probably safe (no §13 trigger). The instant AI VoiceTech's *product* — a CRM sold or licensed to external clients, or embedded white-label on a client's site — contains modified Macro code, §13 is triggered, full stop. Given Rob's actual business model (building products **to sell to clients**, not just an internal tool), (b) and (c) are the realistic scenarios, not (a).

### 3. Scope of the derivative work — where is the line?

Copyright protects **expression**, not **ideas, methods, systems, or processes** (this is codified in US law at 17 U.S.C. §102(b), and was central to *Google LLC v. Oracle America, Inc.*, 593 U.S. ___ (2021)). Architecture patterns, UX flows, "the idea of bidirectional @-linking," "the idea of channel-based permissions" — none of that is copyrightable on its own. What's copyrightable is the *particular expression*: the actual code, actual prose, actual selection-and-arrangement of a database schema, actual UI copy/layout as *pixel-level or markup-level expression* (not the underlying interaction concept).

Going down the ladder from safest to most exposed:

- **Verbatim copying** (copy-paste a file, a function, a whole crate) — unambiguous derivative work / literal infringement absent a license. AGPL attaches immediately.
- **Translation to another language (Rust → TypeScript port)** — **YES, this is a derivative work**, full stop, and this needs to be stated directly because it's the most common self-deception engineers make ("I rewrote it, so it's mine now"). Copyright's definition of "derivative work" explicitly includes *translation* — literally the word used in 17 U.S.C. §101 ("A 'derivative work' is a work based upon one or more preexisting works, such as a translation..."). Courts have applied this to *programming-language translation* the same way as natural-language translation: if you take Macro's Rust logic — its control flow, its specific algorithm, its specific decomposition into functions, its specific error-handling structure — and mechanically re-express it in TypeScript, you have created a derivative work of the Rust original, even though not one token is identical. The AGPL's own definition of "modify" supports this: *"To 'modify' a work means to copy from or adapt all or part of the work in a fashion requiring copyright permission... The resulting work is called a 'modified version'"* (`LICENSE.txt` line 67-70) — "adapt" plainly covers language ports. The closer the port tracks Macro's specific structure (variable-by-variable, function-by-function), the stronger the derivative-work claim; the more it diverges (different architecture, different decomposition, only the *idea* survives), the weaker it gets — but "I translated it faithfully to TS" is presumptively AGPL-encumbered.
- **API/schema copying (Google v. Oracle relevance)** — *Google v. Oracle* held that Google's copying of Java's *declaring code* (API surface — method names, signatures, package structure) to build Android was **fair use**, but critically the Court explicitly **declined to rule on whether APIs are copyrightable at all** — it assumed copyrightability for the sake of argument and won on fair use instead (6-2, April 5, 2021). [Congress.gov CRS summary](https://www.congress.gov/crs-product/LSB10597), accessed 2026-07-25, High confidence (Library of Congress). This matters for Rob because: (1) fair use is a *case-by-case, litigation-tested defense*, not a green light — it does not mean "APIs/schemas are free to copy," it means Google won a specific four-factor balancing test after a decade of litigation; (2) a SQL schema (table names, column names, relationships) is analogous to a declaring-code API — the *names and structure* are more idea/functional than the implementation, but copying it wholesale onto a *directly competing product* (a CRM competing with Macro's own CRM) is the fact pattern that goes the wrong way on Google v. Oracle's fair-use factors (specifically "purpose and character of use" and "effect on the market for the copyrighted work" — the two factors that most favor Oracle-side plaintiffs in commercial-substitute situations). Copying schema *shape* (a Contacts table with name/email/company/deal-stage columns) is low-risk because that's a functional, near-universal CRM data model with minimal creative expression; copying schema *verbatim including Macro-specific column names, constraint logic, migration structure* is higher-risk. There is also no case law on record establishing that a DB schema is *not* copyrightable — merger doctrine (idea and expression merge when there's only one way to express an idea) helps here, but it's not a bright line.
- **Clean-room reimplementation** — the FSF/GPL-family gold standard defense, borrowed from hardware clean-room design (*Compaq's BIOS clone*, *Sega v. Accolade* (1992), *Sony v. Connectix* (2000), all cited as establishing that even intermediate copying during analysis can be fair use *if the final product is independently written* by a team with no access to the original source). [Retro Reversing, "Legality of Reverse Engineering & Clean Room Reversing"](https://www.retroreversing.com/clean-room-reversing), accessed 2026-07-25, Medium confidence (enthusiast/practitioner source, but the case citations are verifiable). Proper clean room requires: (1) one team studies the *behavior* (not the source) and writes a functional spec describing *what* it does, not *how*; (2) a second team, with **no access to Macro's source code at any point**, implements from that spec alone. For a solo founder or small team, true clean-room segregation is operationally hard — if the same engineer who read Macro's Rust also writes the TS, that's not clean-room, that's "read for ideas then implement," which is legally *closer* to safe than a port but still carries residual risk if the implementation ends up structurally similar (courts do look at "substantial similarity" of structure/sequence/organization, not just literal text — this doctrine, from *Whelan v. Jaslow* and narrowed by *Computer Associates v. Altai*'s "abstraction-filtration-comparison" test, is the reason "I didn't copy-paste" isn't a complete defense on its own).

**Practical rule of thumb:** reading code to understand *what it does* and then writing your own implementation from scratch, without the source open in another window, with a materially different structure, is the safest form of "learning from" AGPL code. The more your output tracks Macro's specific expression — file organization, function boundaries, naming, algorithm structure, schema field-for-field — the more it looks like a modified version subject to AGPL, regardless of whether you literally copy-pasted.

### 4. AGPL reach — what happens to Rob's proprietary code in the same repo/binary?

Two governing concepts from the license text:

**Mere aggregation (safe).** `LICENSE.txt` lines 220-226:
> "A compilation of a covered work with other separate and independent works, which are not by their nature extensions of the covered work, and which are not combined with it such as to form a larger program, in or on a volume of a storage or distribution medium, is called an 'aggregate' if the compilation and its resulting copyright are not used to limit the access or legal rights of the compilation's users beyond what the individual works permit. **Inclusion of a covered work in an aggregate does not cause this License to apply to the other parts of the aggregate.**"

Plain English: if Macro's CRM module runs as a *genuinely separate process/service* — e.g., self-hosted Macro as one microservice, and Rob's completely independent proprietary AI-calling engine as a different microservice, talking over a defined API boundary, each capable of standing alone — that's aggregation, and Rob's code stays proprietary. This is the same reasoning that lets Linux (GPL) ship alongside proprietary applications on the same machine: the kernel and the app aren't "combined... to form a larger program."

**Linking/combining (dangerous).** If Rob's proprietary code is **statically or dynamically linked into the same binary/process as Macro code**, imports Macro's internal libraries/crates directly, extends Macro's classes, or is otherwise compiled/bundled such that it forms "a larger program" with Macro's code — that's a combined work, and §5(c) applies: *"You must license the entire work, as a whole, under this License."* The FSF's own guidance (not fetched here but consistent with the license text and universally understood in OSS-compliance practice) treats "same process, shared memory space, function calls across the boundary" as combining; "separate process, network/IPC boundary, each independently distributable" as more defensible as aggregation — though this line is genuinely contested in AGPL compliance circles (some counsel argue a network call between microservices is *not* "combining" even in the same monorepo; others argue tight coupling defeats the argument regardless of process boundary). This is squarely a §8 attorney question if Rob's architecture puts proprietary code anywhere near the same binary as Macro code.

## Business-context conflict Rob needs to know about (not softened)

Rob's standing rule is: **"no upstream attribution — forked/MIT code must not point back to the original author."** This rule is **legally incompatible with AGPL** (and with GPL-family licenses generally), full stop:

- §4 (`LICENSE.txt` lines 187-195) requires anyone conveying the code to *"conspicuously and appropriately publish on each copy an appropriate copyright notice; keep intact all notices stating that this License... appl[ies]... and give all recipients a copy of this License."*
- §5(b) requires modified versions to *"carry prominent notices stating that it is released under this License."*
- §13 requires offering the *Corresponding Source* itself, which by definition includes Macro's original copyright headers throughout the codebase.

**There is no way to strip Macro's attribution and stay in compliance with AGPL.** Attribution and source-offer are not stylistic choices in this license, they are the entire mechanism by which it enforces itself. This is fundamentally different from Rob's MIT-license playbook (where stripping upstream links is a judgment call about *courtesy*, not a legal *requirement* — MIT only requires the license text + copyright notice travel with the *source*, not that a running product's UI credit the author, and most MIT projects Rob has audited/stripped links from are precisely taking advantage of that gap). AGPL closes that gap entirely: if Rob ships anything containing modified Macro (or Twenty) code to anyone outside AI VoiceTech, the "no upstream attribution" rule and AGPL compliance are **mutually exclusive** — he can follow one or the other, not both, on that specific codebase. This is exactly why the risk ladder in §6 pushes toward "read for ideas, clean-room reimplement, or pay for a commercial license" rather than any form of "fork and de-brand."
